title: "Send SMS — India"
description: "Send SMS to Indian numbers through the Omni send endpoint, with DLT fields, campaign tagging, and URL shortening."
---

The Omni send endpoint delivers SMS through the same API used for WhatsApp and RCS. The channel
is determined by the request body: SMS messages are wrapped in an `sms` array.

Because it shares an endpoint with the other channels, this is the API to use if you also send
WhatsApp or RCS, or if you want [fallback](/api-reference/omnichannel/fallback) between them.

<Note>
This API covers **India**, and carries the DLT fields Indian traffic requires. For destinations
outside India, use the [SMS List API](/api-reference/sms-international/send-sms) — a different host with a
different authentication scheme. See [how the two compare](/api-reference/sms/overview#how-it-compares-to-international-sms).
</Note>

## Endpoints

Two send paths are live, and they are separate implementations rather than one aliasing the
other.

| Path | Use it for |
| --- | --- |
| `POST https://api.onexaura.com/send_sms` | The fuller SMS feature set — custom references, campaign tagging, and URL shortening |
| `POST https://api.onexaura.com/oapi/send_sms` | The shared Omni endpoint, also used for WhatsApp and RCS, and required for [channel fallback](/api-reference/omnichannel/fallback) |

Both take the same `apikey` header and the same request body, and everything documented on this
page is supported on `/send_sms`.

<Note>
These are genuinely different handlers rather than a redirect — verified Sept 2026, they return
differently shaped error envelopes for the same rejected key. If a field on this page does not
behave as documented on `/oapi/send_sms`, try it on `/send_sms` before raising it.
</Note>

<Warning>
Call these over **HTTPS**. An `http://` request is answered with a `301` redirect, and a client
that does not follow redirects — or that follows one without re-sending the body — will appear
to send nothing while reporting no error.
</Warning>

## The `sms` array

The `sms` array carries one or more messages in a single call. Each object is one message.

<ParamField body="sms[].sender" type="string" required>
  Sender ID. Must be DLT-approved — see [DLT registration](/guides/sms/dlt).
</ParamField>

<ParamField body="sms[].recipient" type="string" required>
  Recipient mobile number.
</ParamField>

<ParamField body="sms[].messageBody" type="string" required>
  Content of the SMS.
</ParamField>

<ParamField body="sms[].type" type="string" required>
  Message type. **Verified accepted:** `SI`, `OTP`, `SE`. Case-sensitive.
</ParamField>

<Warning>
**`type` is required, and the accepted values are narrower than earlier documentation stated.**
Verified against the live API (Aug 2026):

| Value | Result |
| --- | --- |
| `SI`, `OTP`, `SE` | Accepted |
| `TRANS`, `Promo`, `TXN` | Rejected — `invalid type`, status `700` |
| Lowercase (`si`, `otp`, `se`) | Rejected — the field is case-sensitive |
| Omitted | Rejected — `invalid type` |

`SI` and `SE` correspond to the DLT consent categories Service Implicit and Service Explicit —
see [DLT registration](/guides/sms/dlt#template-types).
</Warning>

<Note>
`Promo` was rejected on the account used for testing, which is provisioned for transactional
traffic. Because the message type is ultimately governed by the API key configuration, `Promo`
may be accepted on a promotional key — this has not been verified.
</Note>

<ParamField body="sms[].templateId" type="string">
  DLT-approved template ID.
</ParamField>

<ParamField body="sms[].entityId" type="string">
  DLT entity ID.
</ParamField>

<ParamField body="sms[].unicode" type="integer">
  `1` for a Unicode message, `0` for normal text. **Required when sending Unicode.**
</ParamField>

<ParamField body="sms[].custRef1 … custRef5" type="string | object">
  Up to five custom references of your own, echoed back on the
  [delivery report](/api-reference/sms/dlr-callback) so you can match a receipt to your own
  record. Each slot takes either a plain string or a nested object:

  ```json
  "custRef1": "order-4821"

  "custRef1": {
    "CustomReference1": "testSMS",
    "CustomReference2": "123"
  }
  ```

  The nested form lets one slot carry several values — useful when five slots are not enough,
  or when you want the pairs kept together.
</ParamField>

<Note>
**The nested object form is supported on SMS only.** WhatsApp and RCS take custom references as
plain values. Sending an object on those channels is not supported.
</Note>

<Warning>
**The message type is ultimately determined by your API key configuration, regardless of the
`type` you send in the request.** If messages are being charged or routed as a different
category than you expect, the API key is the thing to check — not the payload.
</Warning>

<Note>
`templateId` and `entityId` are marked optional in the API, but DLT-regulated traffic in India
will be rejected by the operator without them. Treat them as required for Indian destinations.
See [DLT registration](/guides/sms/dlt).
</Note>

## Top-level fields

<ParamField body="campaignName" type="string">
  Identifier used to group and track messages as a campaign. Set it if you want the send to be
  filterable in [reports](/guides/sms/reports).
</ParamField>

<ParamField body="prefix" type="string">
  Country code applied to recipient numbers — for example `+91`.
</ParamField>

<ParamField body="validation" type="boolean">
  `true` rejects invalid requests outright; `false` processes them anyway.
</ParamField>

<Note>
Set `validation` to `true` while integrating. With `false`, a malformed request is accepted and
fails silently downstream, which is far harder to diagnose than an upfront rejection.
</Note>

## URL shortener

Include the `urlShortener` object when your message contains a link you want shortened and
tracked.

<ParamField body="urlShortener.flag" type="integer">
  `1` enables shortening, `0` disables it. Required if short-URL conversion is needed.
</ParamField>

<ParamField body="urlShortener.urlDetails[].longUrl" type="string">
  The original URL to shorten. Required when `flag` is `1`.
</ParamField>

<ParamField body="urlShortener.urlDetails[].senderId" type="string">
  Sender ID associated with the shortened URL. Required when `flag` is `1`.
</ParamField>

<ParamField body="urlShortener.urlDetails[].domain" type="string">
  Custom domain, if one is configured for your account. Required when `flag` is `1`.
</ParamField>

<ParamField body="urlShortener.urlDetails[].track_user" type="integer">
  `1` enables click tracking, `0` disables it. Required if location tracking is needed.
</ParamField>

Click data captured this way appears in the
[Clicker Data and Clicker Details reports](/guides/sms/reports#clicker-data).

## Response

Both success and failure return **HTTP 200**. The outcome is inside `smsList.sms[]`, one entry
per message in your request.

<CodeGroup>

```json Accepted
{
  "smsList": {
    "sms": [
      {
        "description": "Message submitted with tracking id ( UID )",
        "status": 200,
        "messageid": "01M0QSEJDWTYJTCJ533TRH165A"
      }
    ]
  }
}
```

```json Rejected
{
  "smsList": {
    "sms": [
      {
        "description": "invalid type",
        "status": 700
      }
    ]
  }
}
```

</CodeGroup>

<ResponseField name="smsList.sms[].status" type="integer">
  Per-message result. `200` accepted; `700` rejected.
</ResponseField>

<ResponseField name="smsList.sms[].description" type="string">
  Outcome text — the tracking-id confirmation on success, or the rejection reason.
</ResponseField>

<ResponseField name="smsList.sms[].messageid" type="string">
  Tracking ID, present only when the message was accepted.
</ResponseField>

<Warning>
**The HTTP status tells you nothing about the outcome.** A rejected message still returns
HTTP 200 — the rejection is `smsList.sms[].status: 700` inside the body. Parse the per-message
status; do not branch on the HTTP code.
</Warning>

<Note>
Because `sms` is an array, each message carries its own status. A request with several
recipients can be partly accepted and partly rejected in the same response.
</Note>
