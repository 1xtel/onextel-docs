title: "Send SMS — India"
description: "Send SMS to Indian numbers with DLT fields, custom references, campaign tagging, and URL shortening."
---

Send SMS to Indian numbers. Messages go in an `sms` array, so one request can carry several.

<Note>
This API covers **India**, and carries the DLT fields Indian traffic requires. For destinations
outside India, use the [SMS List API](/api-reference/sms-international/send-sms) — a different host with a
different authentication scheme. See [how the two compare](/api-reference/sms/overview#how-it-compares-to-international-sms).
</Note>

## Endpoint

```
POST https://api.onexaura.com/send_sms
```

<Warning>
Call the endpoint over **HTTPS**. An `http://` request is answered with a `301` redirect, and a
client that does not follow redirects — or that follows one without re-sending the body — will
appear to send nothing while reporting no error.
</Warning>

## Headers

<ParamField header="apikey" type="string" required>
  API key issued by OneXtel.
</ParamField>

<ParamField header="Content-Type" type="string" required>
  Must be `application/json`.
</ParamField>

## The `sms` array

The `sms` array carries one or more messages in a single call. Each object is one message.

<ParamField body="sms[].sender" type="string" required>
  Sender ID. Must be DLT-approved — see [DLT registration](/guides/sms/dlt).
</ParamField>

<ParamField body="sms[].recipient" type="string" required>
  Recipient mobile number.
</ParamField>

<ParamField body="sms[].messageBody" type="string" required>
  Content of the SMS.
</ParamField>

<ParamField body="sms[].type" type="string" required>
  Message type: `SI`, `OTP`, or `SE`. Case-sensitive.
</ParamField>

<Note>
`SI` and `SE` correspond to the DLT consent categories Service Implicit and Service Explicit —
see [DLT registration](/guides/sms/dlt#template-types).
</Note>

<ParamField body="sms[].templateId" type="string">
  DLT-approved template ID.
</ParamField>

<ParamField body="sms[].entityId" type="string">
  DLT entity ID.
</ParamField>

<ParamField body="sms[].unicode" type="integer">
  `1` for a Unicode message, `0` for normal text. **Required when sending Unicode.**
</ParamField>

<ParamField body="sms[].custRef1 … custRef5" type="string | object">
  Up to five custom references of your own, echoed back on the
  [delivery report](/api-reference/sms/dlr-callback) so you can match a receipt to your own
  record. Each slot takes either a plain string or a nested object:

  ```json
  "custRef1": "order-4821"

  "custRef1": {
    "CustomReference1": "testSMS",
    "CustomReference2": "123"
  }
  ```

  The nested form lets one slot carry several values — useful when five slots are not enough,
  or when you want the pairs kept together.
</ParamField>

<Note>
**The nested object form is supported on SMS only.** WhatsApp and RCS take custom references as
plain values. Sending an object on those channels is not supported.
</Note>

<Warning>
**The message type is ultimately determined by your API key configuration, regardless of the
`type` you send in the request.** If messages are being charged or routed as a different
category than you expect, the API key is the thing to check — not the payload.
</Warning>

<Note>
`templateId` and `entityId` are marked optional in the API, but DLT-regulated traffic in India
will be rejected by the operator without them. Treat them as required for Indian destinations.
See [DLT registration](/guides/sms/dlt).
</Note>

## Messaging patterns

The `sms` array covers all three ways of sending:

| Pattern | How to submit |
| --- | --- |
| One-to-one | One recipient in `sms[].recipient` |
| One-to-many | The same message to several recipients — pass them as a comma-separated string in a single `sms[].recipient`, for example `"919999999991,919999999992"` |
| Many-to-many | Different recipients and different content in the same call — add one object per message to the `sms` array |

## Top-level fields

<ParamField body="campaignName" type="string">
  Identifier used to group and track messages as a campaign. Set it if you want the send to be
  filterable in [reports](/guides/sms/reports).
</ParamField>

<ParamField body="prefix" type="string">
  Country code applied to recipient numbers — for example `+91`.
</ParamField>

<ParamField body="validation" type="boolean">
  `true` rejects invalid requests outright; `false` processes them anyway.
</ParamField>

<Note>
Set `validation` to `true` while integrating. With `false`, a malformed request is accepted and
fails silently downstream, which is far harder to diagnose than an upfront rejection.
</Note>

## URL shortener

Include the `urlShortener` object when your message contains a link you want shortened and
tracked.

<ParamField body="urlShortener.flag" type="integer">
  `1` enables shortening, `0` disables it. Required if short-URL conversion is needed.
</ParamField>

<ParamField body="urlShortener.urlDetails[].longUrl" type="string">
  The original URL to shorten. Required when `flag` is `1`.
</ParamField>

<ParamField body="urlShortener.urlDetails[].senderId" type="string">
  Sender ID associated with the shortened URL. Required when `flag` is `1`.
</ParamField>

<ParamField body="urlShortener.urlDetails[].domain" type="string">
  Custom domain, if one is configured for your account. Required when `flag` is `1`.
</ParamField>

<ParamField body="urlShortener.urlDetails[].track_user" type="integer">
  `1` enables click tracking, `0` disables it. Required if location tracking is needed.
</ParamField>

<Note>
Setting `urlShortener.flag` to `1` without an `urlDetails` entry shortens every `http://` or
`https://` link already present in `messageBody`, automatically. Supply `urlDetails` only when
you want to shorten a specific URL and control its domain and tracking separately.
</Note>

Click data captured this way appears in the
[Clicker Data and Clicker Details reports](/guides/sms/reports#clicker-data), and is also pushed
to your own endpoint if you've configured one — see the
[clicker callback](/api-reference/sms/clicker-callback).

## Response

A request with a valid API key returns **HTTP 200**, with one entry per message inside
`smslist.sms[]`. The wrapper key is lowercase `smslist`.

```json Accepted
{
  "smslist": {
    "sms": [
      {
        "description": "Message submitted with tracking id ( UID )",
        "messageid": "3JLkExampleMessageId0000000",
        "status": 200
      }
    ]
  }
}
```

<ResponseField name="smslist.sms[].status" type="integer">
  Per-message result. `200` means the message was accepted for processing.
</ResponseField>

<ResponseField name="smslist.sms[].description" type="string">
  Outcome text — for an accepted message, the tracking-id confirmation.
</ResponseField>

<ResponseField name="smslist.sms[].messageid" type="string">
  Tracking ID for the accepted message.
</ResponseField>

<Warning>
**Accepted is not delivered.** A `200` entry means OneXtel accepted the message for processing —
not that it reached the handset, and not that the recipient number is valid. Confirm the outcome
from the [delivery report](/api-reference/sms/dlr-callback).
</Warning>

### Authentication errors

A request with an invalid API key is rejected with **HTTP 401**, before any message is read:

```json
{
  "status": "Failed",
  "reason": "API_Invalid_Authorisation",
  "code": 401
}
```

## Request errors

These are rejected before any message in the `sms` array is processed:

| Problem | Response |
| --- | --- |
| Unsupported HTTP method | `405`, `API_Method_Not_Allowed` |
| Missing request body | `400`, `API_No_Content` |
| Body is not valid JSON | `400`, `API_Invalid_JSON` |
| Missing `apikey` | `401`, `API_Invalid_Auth_Key` |
| Invalid `apikey` | `401`, `API_Invalid_Authorisation` |
| Unrecognised path | `404`, no response body |

<Warning>
**A missing or empty `sms[].sender`, `sms[].recipient`, `sms[].messageBody`, or `sms[].type`
does not fail the request.** The platform accepts it with `HTTP 200`, and the rejection surfaces
later on the [delivery report](/api-reference/sms/dlr-callback), not here. Set `validation` to
`true` while integrating so these are rejected upfront instead — see
[`validation`](#top-level-fields) above.
</Warning>

## Send via GET

The same endpoint also accepts a `GET` request, with the message passed as query parameters
instead of a JSON body. It carries one message per request — for several messages in one call,
use `POST`.

```
GET https://api.onexaura.com/send_sms
```

<ParamField query="apikey" type="string" required>
  Your OneXtel API key.
</ParamField>

<ParamField query="sender" type="string" required>
  Sender ID. Must be DLT-approved.
</ParamField>

<ParamField query="recipient" type="string" required>
  Recipient mobile number. As with POST, pass a comma-separated list for one-to-many.
</ParamField>

<ParamField query="messageBody" type="string" required>
  Content of the SMS.
</ParamField>

<ParamField query="type" type="string">
  Message type: `SI`, `OTP`, or `SE`. Case-sensitive.
</ParamField>

<ParamField query="templateId" type="string">
  DLT-approved template ID.
</ParamField>

<ParamField query="entityId" type="string">
  DLT entity ID.
</ParamField>

<ParamField query="campaignName" type="string">
  Identifier used to group and track messages as a campaign.
</ParamField>

<ParamField query="urlflag" type="integer">
  The query-string equivalent of `urlShortener.flag` — see [URL shortener](#url-shortener).
</ParamField>

<ParamField query="custref1 … custref5" type="string">
  Up to five custom references, as separate query parameters. Unlike the POST body's `custRef1`,
  these take plain string values only — there is no nested-object form on GET.
</ParamField>

### Example request

```bash cURL
curl --location 'https://api.onexaura.com/send_sms?apikey=YOUR_API_KEY&sender=ONEXTL&recipient=919999999999&messageBody=Your%20code%20is%20123456&campaignName=SMS2026&urlflag=0'
```

### Response

The GET response uses a different shape from the POST response above:

```json Accepted
{
  "status": "SUCCESS",
  "requestId": "3LEHfngZVkPpKMuOLeNg8a9svwE",
  "messages": [
    {
      "status": "SENT",
      "recipient": "919999999999",
      "messageId": "3LEHfn7qH426KqtcrpkEMn6vigq",
      "description": "Message submitted successfully"
    }
  ],
  "campaignName": "SMS2026"
}
```

<ResponseField name="status" type="string">
  Submission result for the request as a whole — for example `SUCCESS`.
</ResponseField>

<ResponseField name="requestId" type="string">
  Identifier for this submission request.
</ResponseField>

<ResponseField name="messages[].status" type="string">
  Per-message result — for example `SENT`.
</ResponseField>

<ResponseField name="messages[].messageId" type="string">
  Tracking ID for the message — the same ID that appears on the
  [delivery report](/api-reference/sms/dlr-callback).
</ResponseField>

<ResponseField name="messages[].description" type="string">
  Outcome text for the message.
</ResponseField>

### Request errors on GET

GET validates more upfront than POST does — several conditions POST accepts with `HTTP 200` are
rejected outright here:

| Problem | Response |
| --- | --- |
| Unsupported HTTP method | `405`, `API_Method_Not_Allowed` |
| Missing `apikey` | `401`, `API_Invalid_Auth_Key` |
| Invalid `apikey` | `401`, `API_Invalid_Authorisation` |
| Missing `recipient` | `400`, `API_Invalid_Recipient` |
| Missing `sender`, or sender invalid for the key | `400`, `API_Invalid_Sender` or `invalid header` |
| Invalid `type` | `400`, `invalid type` |
| Empty `messageBody` | `400`, `API_Invalid_MessageBody` |
| Unrecognised path | `404`, no response body |

<Warning>
**The same condition can behave differently on GET and POST.** A missing `recipient`, for
example, is rejected with `400` on GET but accepted with `200` on POST, with the rejection
surfacing later on the delivery report instead. Don't assume one method's error behavior carries
over to the other.
</Warning>
